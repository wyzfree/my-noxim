# 固定总PE规模下的多芯片扩展实验计划（traffic_table驱动）

## 1. 方案评估（先说结论）
你的方案非常适合毕业论文主线：
1. 目标明确：固定总计算规模（总PE不变），仅改变芯片划分方式。
2. 变量可控：`1x(32x32)`、`4x(16x16)`、`16x(8x8)`三组天然构成扩展实验。
3. 可复现：traffic 从 `traffic_table` 读取，输入可固化成文件。
4. 论文价值高：能直接回答“多芯片并行/多进程交互是否带来速度收益”。

同时要注意一个关键点：
- “多芯片一定更快”不一定成立。多芯片会引入跨芯片通信和同步开销。论文最好的表述应是：
  在哪些负载条件/流量模式下，多芯片方案优于单芯片；在何处出现拐点。

## 2. 实验目标与研究问题

### 2.1 总目标
在总PE固定为 `1024` 时，比较不同芯片划分下的性能与开销：
1. `1 chip x 32x32`
2. `4 chips x 16x16`
3. `16 chips x 8x8`

### 2.2 研究问题（论文可直接使用）
1. 在相同总工作量下，芯片划分对总完成时间（wall-clock）有何影响？
2. 多芯片带来的跨芯片通信开销是否抵消并行收益？
3. 不同流量模式下，性能拐点出现在哪里？

## 3. 公平性设计（必须遵守）
1. 总PE固定：始终 `chips * dimx * dimy = 1024`。
2. 总仿真周期一致：例如统一 `sim=12000` 或更高。
3. traffic随机种子固定：同组实验必须复用同一种子。
4. 每组重复运行至少3次，报告均值与标准差。
5. 结果分开汇报：
   - 仿真统计指标（latency/throughput）
   - 真实运行时间（wall-clock）

## 4. traffic_table设计（建议三类）

### 4.1 T0：无跨芯片对照
- 单芯片与多芯片都跑“仅片内通信”（或极低跨芯片比例）。
- 作用：给出“纯拓扑划分成本”的底线。

### 4.2 T1：邻接链路（你现有生成器可直接支持）
- 模式：`chip i -> chip i+1`。
- 可复用：`traffic_tables/gen_cross_traffic.py`。
- 作用：验证中等跨芯片开销下的扩展趋势。

### 4.3 T2：全局随机跨芯片
- 模式：源/目的芯片随机分布（可控制跨芯片比例 `p_cross`）。
- 作用：压力测试，观察热点和拥塞时多芯片行为。

备注：建议先做 T1 跑通论文主图，再补 T2 提升说服力。

## 5. 指标体系

### 5.1 核心指标
1. `WallClock(s)`：真实运行时长（重点指标，回答“快不快”）。
2. `Avg Latency(cycles)`：平均延迟。
3. `Throughput(flits/cycle)`：系统吞吐。
4. `CrossChipRecords`：跨芯片记录数（从 `chip*_out.txt` 或日志统计）。
5. `Speedup`：相对单芯片加速比 `T_1chip / T_nchips`。

### 5.2 辅助指标
1. 每芯片收发计数（FileIO统计）。
2. 阻塞/等待时间（若日志中有）。

## 6. 执行矩阵（第一版）

固定配置：
- 总PE=`1024`
- sim=`12000`（可后续放大）
- 每组重复3次

实验组：
1. G1: `chips=1,  dimx=32, dimy=32`
2. G2: `chips=4,  dimx=16, dimy=16`
3. G3: `chips=16, dimx=8,  dimy=8`

流量组：
1. L1: 稀疏（sparsity=0.05）
2. L2: 中等（sparsity=0.15）
3. L3: 稠密（sparsity=0.30）

建议先跑：`T1 x (G1,G2,G3) x (L1,L2,L3)`。

## 8. 风险与解释策略（论文加分点）
1. 若16芯片反而变慢：
   - 这是正常结果，说明通信开销超过并行收益。
   - 可通过“负载分区图”展示拐点，结论更真实。
2. 若不同运行波动大：
   - 增加重复次数（3→5），报告误差棒。
3. 若单进程与多进程模式混淆：
   - 在实验章节明确“本组对比的是芯片划分策略在同一执行模式下的表现”。
