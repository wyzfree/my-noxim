# 多进程交互实验设计（执行版）

## 1. 目标与核心思路
本设计用于回答一个核心问题：在 Noxim 多芯片扩展中，仅验证 `chip0 -> chip1 -> chip2` 的单向传递并不能体现并行优势；需要通过“同步时间步协同”和“流水并行协同”展示多进程交互价值。

本文采用两阶段路线：
1. 阶段A：`BSP + Barrier` 同步时间步（主线实验，强调正确性、稳定性、可复现）。
2. 阶段B：`Micro-Batch Pipeline` 微批流水（增强实验，强调吞吐和并行利用率）。

## 2. 实验对象与角色分工
建议使用三芯片逻辑分工：
1. `chip0`：输入侧与聚合侧（输入编码、回传汇总、步推进控制）。
2. `chip1`：中间计算支路A（接收 `chip0` 输入并回传中间结果）。
3. `chip2`：中间计算支路B（接收 `chip0` 输入并回传中间结果）。

此分工可以构造“同一时间步下 chip1/chip2 并行计算”的核心场景。

## 3. 文件通信协议（推荐）

### 3.1 设计原则
1. 单写者原则：每个数据文件只有一个写者，避免写写冲突。
2. 显式完成标志：通过 `done` 文件实现 barrier，而不是靠猜测时序。
3. 步编号隔离：每个时间步单独命名，避免跨步污染。

### 3.2 文件命名
以步 `t` 为例：
1. `chip0_to_chip1.t{t}.txt`（写者 `chip0`，读者 `chip1`）
2. `chip0_to_chip2.t{t}.txt`（写者 `chip0`，读者 `chip2`）
3. `chip1_to_chip0.t{t}.txt`（写者 `chip1`，读者 `chip0`）
4. `chip2_to_chip0.t{t}.txt`（写者 `chip2`，读者 `chip0`）
5. `done_chip0.t{t}`
6. `done_chip1.t{t}`
7. `done_chip2.t{t}`

说明：若你必须保留既有 `fileIO/chipx_out.txt` 机制，可以把以上命名映射到运行目录中的临时文件，不破坏原有功能。

## 4. 阶段A：BSP + Barrier 同步时间步

### 4.1 每步执行流程
对每个 `t in [0, T-1]`：
1. `chip0` 计算第 `t` 步输入 spike/flit，写入 `chip0_to_chip1.t{t}.txt` 与 `chip0_to_chip2.t{t}.txt`。
2. `chip0` 创建 `done_chip0.t{t}`。
3. `chip1/chip2` 轮询 `done_chip0.t{t}`，检测到后分别读取各自输入并计算。
4. `chip1/chip2` 写回 `chip1_to_chip0.t{t}.txt`、`chip2_to_chip0.t{t}.txt`。
5. `chip1/chip2` 分别创建 `done_chip1.t{t}`、`done_chip2.t{t}`。
6. `chip0` 等待两个 `done` 都出现，完成聚合并进入 `t+1`。

### 4.2 正确性约束
1. 任何 chip 只读取“当前步”文件，不预读下一步。
2. 读完当前步后再删除或归档文件，避免重复消费。
3. 日志中必须记录 `step_id`、`records_in/out`、`wait_time_barrier`。

### 4.3 阶段A可回答的问题
1. 多进程交互是否正确闭环。
2. barrier 同步下，各芯片等待比例如何。
3. 在不同注入强度下是否出现拥塞/长等待。

## 5. 阶段B：Micro-Batch Pipeline 微批流水

### 5.1 目的
在保持正确性的前提下，减少 barrier 空等，提高系统吞吐。

### 5.2 执行方式
1. 将样本切分为 `B` 个 micro-batch。
2. `chip0` 按批次发出输入（带 `batch_id`、`step_id`）。
3. `chip1/chip2` 收到即算即回传，不等待全局步完成。
4. `chip0` 依据 `(step_id, batch_id)` 做聚合与顺序提交。

### 5.3 必须新增字段
每条通信记录增加：
1. `step_id`
2. `batch_id`
3. `src_chip`
4. `dst_chip`
5. `payload_len`

### 5.4 阶段B可回答的问题
1. 同样任务量下，流水是否降低总完成时间（makespan）。
2. 吞吐是否提升，且正确率是否保持一致。

## 6. 指标体系与记录格式

### 6.1 主指标
1. `Makespan`：处理固定样本集合的总仿真周期。
2. `Throughput`：单位周期完成的 flit/packet/样本数。
3. `Avg_Latency`：端到端平均延迟。
4. `Barrier_Wait_Ratio`：阶段A中等待占比。
5. `Speedup`：多进程相对基线加速比。

### 6.2 结果一致性指标
1. `Prediction_Match_Rate`：与软件参考结果一致率。
2. `Spike_Count_Diff`：关键层脉冲计数差值。

### 6.3 建议日志字段
建议每步或每批记录：
`timestamp, chip_id, step_id, batch_id, in_records, out_records, compute_cycles, wait_cycles, io_wait_cycles`

## 7. 实验矩阵（建议起步配置）

### 7.1 自变量
1. 负载级别：`low/mid/high`（例如不同 injection rate）。
2. 时间步数：`T = 16, 32, 64`。
3. 微批大小：`B = 1, 2, 4, 8`（阶段B）。

### 7.2 对照组
1. 对照1：单向链路功能流（已有）。
2. 对照2：阶段A（同步时间步）。
3. 对照3：阶段B（微批流水）。

## 9. 论文可直接使用的实验描述（中文模板）
为体现多芯片多进程交互特性，本文在原有单向 flit 传递验证基础上，进一步构建了基于时间步的协同计算任务。首先采用 BSP+Barrier 机制，在每个时间步内由 chip0 产生输入并分发至 chip1 与 chip2 并行计算，再由二者回传结果至 chip0 聚合，从而形成“分发-并行计算-回传-同步推进”的闭环。随后引入 micro-batch pipeline 机制，将样本按批次重叠执行，减少全局同步等待。实验从总完成时间、吞吐、平均延迟、等待占比与结果一致性等维度进行评估，以验证多进程交互在高负载条件下的可扩展性收益。

## 10. 立即执行清单（按优先级）
1. 落地阶段A：先做 `step_id + done/barrier`，跑通稳定闭环。
2. 补齐日志：把 `wait_cycles/io_wait_cycles` 写入每 chip 日志。
3. 建立评测脚本：汇总 makespan、吞吐、延迟、一致性。
4. 跑阶段A实验矩阵并出图。
5. 落地阶段B：加入 `batch_id` 并实现重叠执行。
6. 对比 A/B，形成论文实验结论。
